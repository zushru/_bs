## Resolved ReqRing stale-ticket and failure-result cache gaps (v0.2.67–v0.2.68)

- `ReqRing::finish()` and `abort()` previously matched only req_id. After `expire()` freed a pending entry, the same req_id could be reserved again; a late old handler could then complete or clear the new reservation.
- v0.2.67 assigns a nonzero 64-bit ticket to each new reservation and requires req_id plus ticket for finish/abort. A regression reuses the same req_id and fingerprint, then proves stale completion and abort leave the new reservation pending.
- v0.2.67 adds reservation tickets; v0.2.68 adds a boolean `finish()` result and rejects every code except `A_OK`, leaving failed results pending for explicit abort. Regression coverage verifies both stale-ticket protection and retry after a non-success finish.
- `test_api` passes 41/41. This is a RAM-only core helper; there is no production caller. Expiry does not cancel the old handler, and ReqRing is not durable exactly-once protection. U112 remains unresolved.

## Resolved API pointer-boundary crashes and ambiguous fingerprint errors (v0.2.66)

- `buildMark()` and `buildNoClass()` previously wrote through `Event* out` on valid requests without checking null. The three `RosterStore::plan*()` methods did the same; `RosterStore::nameOf()` copied to its destination without checking null.
- `reqFingerprint()` previously returned a bare uint32 digest and dereferenced its input for the requested length. It had no non-colliding way to report invalid null/nonzero input.
- v0.2.66 adds explicit checked fingerprint output, null destination rejection on event builders, appended `RE_BAD_OUTPUT` for roster planning (preserving old enum values), and a null `nameOf()` destination guard. Counts remain zero on rejected event plans.
- Focused PlatformIO verification passed 77/77 across four suites, including the month projection consumer. This remains host evidence: no production HTTP adapter or ESP32 target build exists. Null guards do not validate dangling pointers, undersized buffers, or arbitrary invalid non-null addresses.

## Resolved token API null-pointer crash (v0.2.65)

- `TokenTable::check()` previously dereferenced a null token pointer; `revoke()` reached `ctEqual()` with a null pointer whenever a session was active. Both could crash the process. The public `ctEqual()` helper also dereferenced null inputs for nonzero lengths.
- v0.2.65 rejects null token checks, treats null revocation as a no-op, and returns false from `ctEqual()` for null/nonzero-length inputs. Zero-length equality remains true.
- The regression crashed with SIGSEGV before the fix and passed after it. It also verifies that valid sessions remain active and that null calls do not alter LRU eviction order. `test_api` and `test_pin_auth_session` passed 49/49.
- This is core API hardening only. It does not implement the absent production HTTP/session boundary (C6), nor does host testing prove an ESP32 target build or hardware behavior.

## Resolved core lockout arithmetic defect (v0.2.64)

- A valid uint32 seconds lockout deadline can wrap to zero. The previous PinLockout used zero as its unlocked sentinel, so this exact boundary bypassed the lock.
- v0.2.64 adds an independent locked_ flag and a red-to-green host regression for failure and reboot paths. The persisted counter and duration policy are unchanged.
- This resolves only the arithmetic sentinel defect. C6 remains blocking: no production HTTP/boot caller, PIN verifier/writer or protected routes exist; no target or physical-device verification was performed.
