# SPEC: first-run setup request decoder and HTTP candidate

Status: **source-authored, not composed into the target**. The boot shell remains GET-only. E15 delegates concrete endpoint schemas; this document records the current engineering proposal, not a user-signed API contract.

## Proposed endpoint

- Method/path: `POST /api/v1/setup`
- Scope: `CFG_BOOT_NEEDS_SETUP` only.
- Content type: exactly `application/json`.
- Require one decimal `Content-Length` from 1 through 768 bytes. Transfer-Encoding and chunked bodies are rejected.
- The proposed ESP32 adapter uses the framework's `HTTPRaw` path and a fixed 769-byte buffer, not `arg("plain")`. Its eventual owner must call `collectHeaders()` for `Content-Type`, `Content-Length` and `Transfer-Encoding` before serving requests; no target owner currently does this.
- Successful boundary completion returns `202` with `{"status":"provisioned","reboot":"pending"}`; it never returns the setup code or initial PIN. The fresh-boot gate handles display clearing and restart after the HTTP callback returns.

## Strict request schema

All root and config properties are required exactly once. Unknown keys, duplicate keys, missing keys, trailing commas/data, escaped strings, non-ASCII strings, floating-point/exponent numbers and wrong JSON types are rejected.

```json
{
  "setup_code": "six ASCII digits",
  "initial_pin": "six ASCII digits",
  "config": {
    "utc_offset_min": 480,
    "late_min": 30,
    "scan_lead_min": 30,
    "term_start_day": 100,
    "term_end_day": 400,
    "auto_sync": 1,
    "sound_mode": 0,
    "timetable": [
      [[480, 750, true], [810, 990, true]],
      [[480, 750, true], [810, 990, true]],
      [[480, 750, true], [810, 990, true]],
      [[480, 750, true], [810, 990, true]],
      [[480, 750, true], [810, 990, true]]
    ]
  }
}
```

- `setup_code` and `initial_pin`: exactly six ASCII decimal digits. The existing first-run boundary enforces PIN weakness policy and the signed E33 code lifecycle/lockout.
- `utc_offset_min`: -720..840; `late_min`: 0..240; `scan_lead_min`: 0..60.
- `term_start_day` / `term_end_day`: inclusive local day numbers since 2020-01-01; both are 0..31446 and end may equal start for a one-day term (E26, delegated); 31446 is 2106-02-05, the last full local day safe for uint32 Unix timestamps at every supported offset.
- `auto_sync`: integer 0 or 1. `sound_mode`: integer 0..2.
- `timetable`: five weekday arrays Monday through Friday; each has two slots in AM/PM order. Each slot is `[startMinute, endMinute, enabled]`; the enabled member must be a JSON boolean. Existing Config validation applies all detailed schedule rules.

The following are deliberately not request fields:
- `wifiPass`: taken from the exact existing AP bootstrap credential by `ApCredentialSetupCoordinator`; never trust a caller-provided value.
- `pinSet`, `pinSalt`, `pinHash`: generated by the initial PIN preparer after E33 code verification, durable attempt-counter reset and H_UNPROVISIONED authorization.
- `minScore`: remains the current default value 0; the client cannot silently choose an unapproved sensor threshold.

## Parser and boundary ownership

decodeFirstRunSetupRequest() is a pure core decoder with a fixed 768-byte limit. It writes its output only on success and exposes a wipe helper for the decoded credentials/config. Its native test source covers schema completeness, exact types/ranges, duplicate/unknown keys, escape rejection, trailing commas/data, request length and wiping; these registrations are NOT RUN.

FirstRunSetupBodyBuffer is a hardware-independent fixed-capacity accumulator for the raw callback. It accepts a declared length from 1 through 768 bytes, verifies each chunk cumulative total against the prior received length plus currentSize before copying, rejects null/empty chunks and any declared/capacity overrun, and exposes its contents only after finish() confirms the exact length. abort(), malformed chunk/length failures, incomplete finish, clear() and destruction wipe the complete buffer. The helper does not parse JSON or authorize provisioning. Six native regressions cover split chunks, data exposure only after finish, invalid state and lengths, cumulative-size mismatch, null/empty chunks, overflow, incomplete/abort and clean reuse; they are registered but NOT RUN.

Esp32FirstRunHttpHandler delegates raw body assembly to FirstRunSetupBodyBuffer; it still checks Content-Length, Content-Type and Transfer-Encoding, records parse-time rejection without writing a response, then emits that response in the normal RequestHandler phase after WebServer has cleared per-request response headers. It dispatches successful bodies only through the existing FirstRunSetupCodeBoundary. In the pinned WebServer 3.3.12 API, HTTPRaw.buf is an inline fixed array and totalSize is cumulative, so the adapter passes those values to the helper and does not perform an impossible null check on the inline array. Its multipart upload callback refuses file uploads. The handler remains a source candidate and is not constructed or registered by main.cpp; the boot shell remains GET-only.
## Framework parser guard — source-authored, not yet applied

The pinned Arduino-ESP32 WebServer parser selects HTTPRaw only for non-multipart bodies by default. Multipart requests otherwise reach _parseForm() before route dispatch; that function ignores its total Content-Length argument and accumulates field values in String objects. The ordinary body path also allocates from the declared length. A route-level limit is too late.

The attendance PlatformIO environment now references tools/apply_pinned_webserver_patch.py as a pre-build script. The script is pinned to Espressif32 8.0.0's installed Arduino framework package version 4.30312.261024, WebServer 3.3.12, and the exact original Parsing.cpp SHA-256. It fails closed on any drift and applies a narrow source transformation only when the attendance target is built. The patch:
- requires every POST/PUT/PATCH/DELETE request to match an explicit canRaw() handler; otherwise it returns 405 before body parsing;
- dispatches an opted-in raw handler before the multipart parser, so the setup handler can reject non-JSON content at RAW_START;
- rejects duplicate Content-Length, duplicate Content-Type and any Transfer-Encoding on raw-handled mutation requests;
- caps raw bodies at 768 bytes and uses one 5,000 ms whole-body deadline with available-byte-limited reads; negative Content-Length returns 400, oversized bodies return 413, connected no-progress/deadline paths return 408, and disconnect paths emit RAW_ABORTED without attempting a response.

The script saves the exact original framework source, restores it on normal SCons/Python process exit, and retains a hash-checked backup for recovery after abnormal termination. It has NOT been run; the installed package has not been modified in this increment. Because PlatformIO's framework package is shared, do not run another PlatformIO build concurrently while this pre-build patch is active. If a build process is forcibly terminated, recover the retained original backup before running any unrelated build. The future handler owner must still collect Content-Type, Content-Length and Transfer-Encoding before handling requests. The target remains GET-only, and the POST handler remains unconstructed/unregistered. The framework patch itself is source-authored but not compiled or executed.

Plain HTTP on the protected SoftAP follows the signed network threat model; the handler must not log or echo secrets. The source candidate, patch script and decoder tests are not compile/runtime evidence. Tests, static checker, compiler, target build, flash and hardware remain NOT RUN.
