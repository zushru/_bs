## 11. Arduino startup and NVS erase risk (C34)

Pinned Arduino-ESP32 3.3.12 calls `initArduino()` from `app_main()` before the sketch `setup()`. Its `initArduino()` invokes `nvs_flash_init()` and, on `ESP_ERR_NVS_NO_FREE_PAGES` or `ESP_ERR_NVS_NEW_VERSION_FOUND`, attempts to erase the entire default DATA_NVS partition with `esp_partition_erase_range(partition, 0, partition->size)` before retrying. A guard placed in `setup()` is too late. This is a data-integrity blocker for any firmware using the unmodified startup path.

v0.2.48 uses shared `Esp32NvsStartupGuard` linker wrappers around `nvs_flash_init` and `esp_partition_erase_range` in both compile/link targets. The wrapper captures the first NVS init result and blocks the known Arduino startup fallback that requests one whole DATA_NVS partition erase call. It intentionally permits normal sector erase calls. This is a narrow interception, not a generic erase firewall: explicit `nvs_flash_erase()` or a sequence of sector erases is not blocked. Both target builds succeeded in the remote PRoot environment; the smoke ELF routing inspector passed. The final probe ELF still needs inspection, and no device output exists. Production boot wiring remains absent.



## 12. v0.2.48 shared NVS startup guard and Codespaces

`Esp32NvsStartupGuard` is now a reusable HAL adapter in `lib/hal_esp32/src`. Its policy tests are hardware-independent. The implementation is compiled only for `ARDUINO_ARCH_ESP32`; native environments see an empty translation unit. Both target configurations link `--wrap=nvs_flash_init` and `--wrap=esp_partition_erase_range`, and the smoke/probe applications check the latched status before application setup work. The diagnostic probe does not mount application storage or run attendance tasks.

The wrappers are not a complete production boot owner. Any production Arduino-ESP32 target must include the wrapper object, inspect its final ELF for the exact framework call routing, check status before any app NVS use, and define its fail-closed health/fault behavior. Do not deliberately induce an NVS migration error or erase on the user's only device.

Codespaces setup is described in `docs/CODESPACES.md`; the import process that preserves the old `main` branch is in `CODESPACES_IMPORT.md`. Use the 2-core machine initially. The Codespaces ESP32 script performs compile/link only and does not flash.
