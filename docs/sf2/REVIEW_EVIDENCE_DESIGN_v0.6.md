# SF2 learner-identity review evidence — architecture v0.6

Status: **D4 policy design complete; implementation blocked.** This document consolidates the signed and delegated D4 decisions. It does not implement a reviewer verifier, metadata store, HTTP adapter, UI, backup component, or XLSX export. The selected threat boundary remains protection against unauthorized Wi-Fi clients only. Physical flash access/modification and malicious authenticated administrators are out of scope.

## 1. Product goals

The workflow must be quick for an authorized administrator and difficult to complete accidentally:

- One administrator may enter and review the same learner record. This is **self-review**, not independent verification.
- The administrator chooses the source type(s) used. The system does not require document uploads, document numbers, arbitrary references, or a typed reviewer identity.
- One confirmation covers all populated identity fields. Do not make the administrator tick a separate box for every name component.
- Missing report-required data remains visible and blocks final reporting, but does not block fingerprint enrollment or attendance recording.
- A review applies only to the exact immutable identity revision that was displayed and confirmed.
- Any correction creates a new revision and requires a new review. Old revisions and old review records remain available for historical reconstruction.

## 2. What the review means

The strongest permissible claim under the selected shared-admin-credential model is:

> An authenticated `ADMIN` session recorded a self-review of the populated identity fields for this exact learner-identity revision, using the declared source category or categories.

It does **not** prove:

- which individual human used the shared admin credential;
- that a source document is authentic;
- that the chosen source category is accepted by DepEd/LIS or the school;
- that a learner personally presented the document;
- that the device's physical storage was not modified.

Never use `VERIFIED`, `INDEPENDENTLY_VERIFIED`, `TWO_PERSON_APPROVED`, or `NON_REPUDIABLE` for this workflow. `SOURCE_CHECKED` in existing metadata is only a caller-supplied legacy claim and cannot authorize a report.

## 3. Source categories — D4-4 (DELEGATED)

Use four broad built-in categories:

| Value | UI label | Meaning |
|---|---|---|
| `SCHOOL_RECORD` | School-maintained record | A learner record maintained by the school, such as its current learner-information or enrollment record |
| `GOVERNMENT_DOCUMENT` | Government-issued record/document | A record/document issued by a government office |
| `GUARDIAN_SUBMISSION` | Parent/guardian submission | Information or a document supplied by a parent or guardian |
| `OTHER_SCHOOL_ACCEPTED_SOURCE` | Other source accepted by the school | Another source the school says it accepts; no free-text description is collected |

The source categories are a compact classification, **not an official DepEd evidence list or a hierarchy of legal authority**.

### One-time school configuration

- Present the four categories in one setup screen, all selected initially.
- The administrator can disable any category the school does not accept.
- Require one explicit confirmation: “These are the source types this school permits for identity review.”
- The accepted category set is school-configurable policy. Its configuration is still an administrator declaration; do not describe it as independently approved by DepEd/LIS.
- Every review must select at least one currently enabled category. Multiple categories are allowed when more than one source was actually consulted.
- Changing the accepted set increments a source-policy revision. If a previously used category is later disabled, reviews relying on that category become stale for new report generation and require review against an enabled category.

### Evidence minimization

Do not collect or persist:

- document photographs, scans, or uploads;
- government/document/credential numbers;
- unrestricted evidence references or free-text descriptions;
- source-document contents;
- reviewer names, initials, or self-entered staff IDs.

The selected category is a self-declared source classification, not proof that the document was inspected or authentic. No evidence locator is required in this release. This is the convenience-first, data-minimizing choice; school-specific policy changes can be handled by changing the accepted category set, not by adding document attachments.

## 4. Review scope and administrator workflow

### Required identity fields

- Review scope is generated by the system as **all populated canonical identity fields**: `legalName.firstName`, `middleName`, `lastName`, `extensionName`, `lrn`, and `sex`.
- Empty optional fields are not listed as reviewed.
- The user does not manually tick fields. The server derives the review scope from the immutable identity record it is about to commit.
- Report completeness is a separate calculation. The required field set must come from the approved target SF2 template/profile. Do not invent LRN/sex/name requiredness from the reference workbook. Until that mapping is settled, an identity may be self-reviewed but cannot be declared complete for an authoritative report.

### Intended UI flow

1. Administrator opens the learner's reporting identity.
2. The screen shows the learner's operational device ID separately from the legal reporting fields. Operational display names are not copied into legal-name fields.
3. The screen highlights missing or malformed values and displays the exact values to be reviewed.
4. Administrator selects one or more enabled source categories.
5. Administrator taps one confirmation: “I checked all displayed identity details against the selected source(s).”
6. The authenticated server action records `actorRole=ADMIN`, `reviewMode=SELF_REVIEW`, the exact identity revision, the generated populated-field set, the source categories, and the committed metadata sequence.

No individual reviewer name is requested. No review action may be created by a public route or from a browser-supplied `verified`/`reviewed` boolean. The server must derive the learner identity and field set from its own source records.

### Independent status axes

Review status and report completeness are separate. Do not collapse them into one state.

| Review status | Meaning | Reporting effect |
|---|---|---|
| `DRAFT` | No review exists for the current identity revision | Identity-review gate not met |
| `SELF_REVIEWED` | Authenticated administrator self-reviewed all populated fields in the current revision | Identity-review gate may pass; other report checks still apply |
| `REVIEW_STALE` | Identity changed, or a selected source category is no longer permitted | Identity-review gate not met; repeat review |

Separately calculate `reportIdentityCompleteness` as `COMPLETE` or `INCOMPLETE` from the target report's required-field rules. A learner can legitimately be `SELF_REVIEWED` while report completeness is `INCOMPLETE`; that must never block ordinary attendance. Adding an allowed source category does not invalidate older reviews. Disabling a category used by a review makes that review stale. Store the policy revision for audit, but evaluate continued validity against the currently enabled category set.

`SELF_REVIEWED` is intentionally not named `VERIFIED`.

## 5. Time and ordering — D4-5 (DELEGATED)

- The authoritative order is the tuple **(metadata-store lineage, committed metadata transaction revision, change index within that transaction)**. The change index prevents two review actions committed in one multi-change transaction from becoming indistinguishable.
- A review is not successful until the metadata transaction's commit procedure succeeds. A failed or ambiguous commit must not show `SELF_REVIEWED`. Report-field completeness is evaluated separately; missing fields do not turn a valid self-review into a false review, but they still block final reporting.
- The review record binds to the exact learner identity record ID and identity revision, and captures the source-policy revision used for the decision. The server assigns the review order tuple; no part of it is accepted from the browser.
- The DS3231 calendar time may be retained as an optional diagnostic observation with an explicit quality marker `UNTRUSTED_RTC`. It must be displayed as “device clock — not verified” and must never determine review validity, ordering, effective date, report month, or export authorization.
- If the RTC is invalid or unavailable, omit the observation; do not block review solely because the clock is unavailable.
- Monotonic runtime ticks are not persisted as calendar evidence and cannot order events across reboot.
- The order tuple is a commit-order receipt, not a cryptographic signature or proof against physical modification. A new/unproven store lineage makes old review order incomparable; prior review state must be treated as missing unless the lineage and history are recovered together.
- After a metadata store is reset, replaced, restored without a validated lineage, or otherwise loses its revision history, all prior review state is treated as missing. Do not reconstruct order from RTC timestamps.

## 6. Revision and correction — D4-7 (DELEGATED)

- Every persisted change to a legal-name component, LRN, sex, identity record ID, or identity effective interval creates a new immutable identity revision.
- The old review remains attached to the old revision only. It never carries forward to the corrected revision.
- The corrected revision starts in `DRAFT` and needs a new self-review.
- If a previously selected source category is later disabled by school policy, that review becomes `REVIEW_STALE` for new report generation. Adding a category does not stale existing reviews.
- Preserve old identity revisions and old review records. Do not rewrite history or silently replace values in a prior snapshot.
- Each generated report snapshot must be pinned to its exact metadata revision. A later correction does not mutate that snapshot.
- If a correction's effective interval intersects a previously generated report month, mark the old snapshot as requiring an administrator's review/re-generation decision. Do not silently regenerate, silently revoke, or claim that an already-submitted DepEd form has been amended. Formal re-submission rules remain school-dependent.
- Movement-history changes do not automatically invalidate the learner's name/LRN/sex review; movement completeness has its own report gate. Do not conflate identity review with enrollment/movement verification.

## 7. Persistence and backup — D4-8 (DELEGATED; hard implementation gate)

**O8 remains SIGNED and unchanged: the device backup contains config + roster + attendance log.** Do not add reporting PII to that bundle under this release.

Selected interim rule:

- Do not persist legal names, LRN, sex, source categories, review records, or movement details on the ESP32.
- Do not put them in the ordinary attendance log, NVS config, browser localStorage/IndexedDB, service-worker cache, URLs, serial logs, or debug logs.
- Do not expose them through an HTTP route or export them to XLSX.
- A future prototype form may use volatile memory only; it must warn that data will be lost on reload/restart and must not present itself as a usable attendance/reporting record.
- Authoritative SF2 export remains disabled until the user explicitly approves either an amendment to O8 or a separately specified companion backup/recovery workflow that preserves metadata and attendance as one recoverable reporting set.

This choice preserves the signed backup contract but means reporting identity cannot yet be a production feature. That is an intentional blocker, not an implementation omission to work around.

## 8. Candidate logical review record (not a wire/storage schema)

```json
{
  "learnerId": 17,
  "identityRecordId": "identity-record-id",
  "identityRevision": 12,
  "sourcePolicyRevision": 2,
  "metadataLineage": "illustrative-lineage-id",
  "reviewOrder": { "metadataRevision": 13, "changeIndex": 2 },
  "actorRole": "ADMIN",
  "reviewMode": "SELF_REVIEW",
  "sourceCategories": ["SCHOOL_RECORD"],
  "reviewScope": "ALL_POPULATED_IDENTITY_FIELDS",
  "reviewedFields": ["legalName.firstName", "legalName.lastName", "lrn", "sex"],
  "rtcObservedAt": "2026-11-07T10:30:00+08:00",
  "rtcTimeQuality": "UNTRUSTED_RTC"
}
```

The identifiers and numbers above are illustrative only. `metadataLineage` and `reviewOrder` are assigned by the server/storage coordinator; `changeIndex` is the operation position within the committed transaction. They are not accepted from the browser. `rtcObservedAt` is optional. The final wire shape, field widths, identifier generation and persistence encoding are not approved. Never persist session tokens, PINs or raw authentication material in this record.

## 9. Remaining implementation gates

D4's **policy choices** are now resolved as signed or delegated entries. Production implementation remains blocked by:

- C6: HTTP/JSON adapter enforcement of admin token, PIN lockout, persist-before-verify and old-PIN checks;
- C13: actual LittleFS/transaction power-loss behavior;
- C24/C25/C30/E27: complete and trustworthy source roster/event history;
- C26: metadata persistence, capacity, replay, migration and transaction durability;
- C27: route-level authorization, no-store, redaction and no-PII logging;
- C28: bounded snapshot paging and target loop-latency proof;
- C29/O8: approved metadata backup and restore path;
- C31: server-side source construction and review gate; browser-supplied state is untrusted;
- official SHS template and school-dependent reporting policy acceptance.

D3 remains `INCOMPLETE`; calculation remains `PREVIEW_READY`; `authoritativeExportReady` remains `false`. This document does not authorize PII persistence, an HTTP endpoint, or an XLSX export.
