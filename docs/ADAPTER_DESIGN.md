# Hardware and HTTP adapter design register

Status: interface design only where marked. This file separates the core contracts from target-specific implementations. Do not treat a planned backend as implemented.

### Token issuance and entropy source (v0.2.38)

`TokenSessionSuccessAction` is the current core bridge from `PinAuthCoordinator` to the existing RAM-only `TokenTable`. It requests exactly 16 bytes from `ISecureRandomSource` after the coordinator has durably reset the attempt counter, then calls read-only `TokenTable::canIssue()`; it does **not** insert the token or evict a current session yet. It treats RNG failure, all-zero output or duplicate-token refusal as `PA_INDETERMINATE` so the coordinator latches. It permits one token copy into the HTTP response. The response handler must call `confirmResponseSent(monotonicNowS)` only after the complete response write succeeds; only then does the action call `TokenTable::issue(monotonicNowS)`, and only then can a live LRU session be displaced. If the handler aborts or the action is destroyed before confirmation, the pending token is cleared and the table remains unchanged. The handler must erase its temporary copy after use. Pass current monotonic seconds at confirmation so the 900-second idle timer starts when the token is activated, not when PIN checking began. The route must not yield to another `TokenTable` mutation between preflight and confirmation; if an unexpected `issue()` failure occurs at confirmation, treat it as an authentication/service fault, not a successful login. This serialized-use contract has no production HTTP implementation or test yet.

`Esp32SecureRandom` wraps the ESP-IDF `esp_fill_random(void*, size_t)` API. It refuses requests until `notifyRfStarted()` has been called and returns to the blocked state on `notifyRfStopped()`. The production caller must signal start only after `esp_wifi_start()` or the selected Wi-Fi AP start operation has succeeded; the adapter cannot query the actual RF state. Its readiness field is a plain `bool`, so notifications and `fill()` must run on one serialized task unless a target-verified synchronization primitive is added for cross-task use. Espressif documents that `esp_random()`/`esp_fill_random()` provide true random output while Wi-Fi or Bluetooth is enabled; without a continuous entropy source they must be treated as pseudorandom. API reference: https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-reference/system/random.html. The actual Arduino-ESP32/ESP-IDF version is not pinned in this source tree, and this adapter has not had an ESP32 target build.

Access token table remains RAM-only by product rule. No sensor password is changed or persisted by this adapter. v0.2.31 adds `PinAuthCoordinator`; v0.2.34 adds `Esp32NvsPinAttemptStore`. The adapter stores the exact `uint16_t` value under `pin_fails` in a caller-selected namespace, rejects the existing `attcfg` config namespace, and requires `nvs_commit()`, handle close, fresh read-only reopen and exact value read-back before returning success. It does not call `nvs_flash_init()`; the application must initialize NVS first (the existing `Esp32NvsConfigBackend::begin()` calls it). A missing/wrong-type key is a fault, not zero. `initializeFailureCount()` is a separate first-provisioning-only operation: call it only after `ConfigBootCoordinator::needsSetup()` reports a genuine first setup and before setup-code requests are accepted. Never call it to recover a missing counter on a previously provisioned device. This is a caller gate, not an anti-tamper guarantee; physical flash access remains outside signed R11 scope. Commit/read-back does not prove power-cut behavior. Construct one long-lived coordinator for each counter domain chosen under E12 and call `boot()` before serving any corresponding route; never create one per request. The E12 counter-domain allocation remains DELEGATED: the adapter supports separate namespace instances without deciding whether PIN and setup-code attempts share a domain. The config blob contains the Wi-Fi passphrase, PIN hash and PIN salt; do not log or expose raw slot bytes. `Esp32WifiAp` accepts only the validated caller-supplied Wi-Fi credentials. v0.2.41 adds the separate E28 bootstrap source via `ApCredentialBootstrap`, `Esp32NvsApCredentialStore` and `Esp32BootstrapRandom`; production boot/OLED wiring is still absent. E29 is SIGNED (`att`); E31 is DELEGATED (channel 1). E30 is DELEGATED to no remote reset/rotation; USB service recovery is not implemented. v0.2.13 implements the proposed namespace/key names and adds `ConfigProvisioner` for the first valid config at slot A/generation 1 behind an injected setup authorization gate. v0.2.15 adds `ConfigBootCoordinator`, which is the required wrapper: it calls backend begin/load, exposes no config on blank/fault state, provisions only from NEEDS_SETUP, and reloads through the canonical backend path before entering READY. Before writing, the provisioner independently checks the durable `ATTP` marker as well as both slots; a surviving marker or marker read error blocks reprovisioning. NVS encryption state is unknown: no production build configuration, key partition or eFuse provisioning is present here; see C16. The adapter does not erase the partition and treats malformed-length blobs as faults.

Backend requirements: distinguish missing keys from real NVS errors; never erase the NVS partition as recovery; never treat a failed read as a blank slot; commit the inactive slot; close/reopen and decode it before switching live state. `Esp32NvsConfigBackend` implements `IConfigSlotBackend` plus the provision-only `IConfigProvisionBackend` capability, providing `begin()`, `load()`, `readSlot()`, `writeSlot()` and `readProvisionMarker()`; the last method distinguishes an absent marker from a valid existing marker and treats malformed/read-error states as failure. The config coordinator performs the separate read-back/decode/content check. Exact target build and power-cut behavior remain unverified. Coordinator contract is in `docs/SPECS/config_apply.md`.

### SoftAP lifecycle and entropy owners (v0.2.41)

`Esp32WifiAp` is the intended sole owner of the ESP-IDF SoftAP lifecycle and the `Esp32SecureRandom` readiness transition. v0.2.41 adds a separate `Esp32BootstrapRandom` for pre-radio first-provision credential generation; do not use the RF-gated token RNG before AP_START. It accepts caller-supplied SSID/passphrase, enforces SSID 1–32 bytes, passphrase 8–63 printable ASCII, explicit channel 1–13, broadcast SSID and max two clients. No credential default is embedded. The bounded `wifi_config_t` temporary is volatile-cleared after `esp_wifi_set_config()`. Startup installs `WIFI_AUTH_WPA2_PSK` and `WIFI_CIPHER_TYPE_CCMP` before `esp_wifi_start()`; the RNG gate opens only after `WIFI_EVENT_AP_START`. Stop closes the RNG gate before `esp_wifi_stop()`. The adapter and RNG fill path must stay on one serialized task.

The production path must not call Arduino `WiFi.mode()` or `WiFi.softAP()`. Source review of Arduino-ESP32 3.3.12 showed `WiFiAPClass::softAP()` calls `AP.begin()` before `AP.create()`; that path starts AP mode and waits for AP_START before applying the caller's new `wifi_config_t`. The v0.2.39 adapter therefore uses direct ESP-IDF calls: `esp_netif_init()`, default event loop, checked `esp_netif_new()` using explicit `base = ESP_NETIF_BASE_DEFAULT_WIFI_AP`, `driver = nullptr` and `stack = ESP_NETIF_NETSTACK_DEFAULT_WIFI_AP` fields, then `esp_netif_attach_wifi_ap()`, `esp_wifi_set_default_wifi_ap_handlers()`, `esp_wifi_init()`, `esp_wifi_set_storage(WIFI_STORAGE_RAM)`, `esp_wifi_set_mode(WIFI_MODE_AP)`, `esp_wifi_set_config(WIFI_IF_AP, ...)`, then `esp_wifi_start()` and AP_START wait. It includes `esp_wifi_default.h` explicitly for the netif/Wi-Fi helper declarations. The checked lower-level netif setup avoids `esp_netif_create_default_wifi_ap()`, which is documented to use `assert()`/`ESP_ERROR_CHECK` and abort on setup failures. Teardown also avoids the `void` `esp_netif_destroy_default_wifi()` wrapper: `cleanup_()` now calls `esp_wifi_clear_default_wifi_driver_and_handlers()` directly, retains the netif on a non-`ESP_OK` result, and invokes `esp_netif_destroy()` only after successful clear. This prevents the wrapper from discarding a cleanup error and unconditionally destroying a possibly still-attached netif. These APIs were reviewed against ESP-IDF v5.5.5; no target build or first-beacon capture exists.

The adapter assumes sole ownership of the Wi-Fi driver/AP netif. Do not mix it with another `esp_wifi_init()`, `esp_netif_attach_wifi_ap()` or Arduino Wi-Fi startup. The AP_START callback only signals an EventGroup; the serialized caller opens `Esp32SecureRandom` after the wait. `rfStarted_` is not a cross-task synchronization primitive. The adapter is not production-wired.

**E28 is SIGNED and implemented at adapter/core level only.** `ApCredentialBootstrap` generates 128 random bits with the ESP-IDF SAR-ADC entropy source on `CFG_BOOT_NEEDS_SETUP`, stores a 32-character lowercase-hex passphrase under `attwifi/ap_pass_v1`, reads it back, and returns `disclose=true` on every setup-required boot. On `CFG_BOOT_READY`, validated `Config::wifiPass` is authoritative and is copied into the separate store only if missing; an existing mismatch fails closed. The production caller must display `Wi-Fi: att` and the secret on the OLED before setup reaches READY. v0.2.44 adds the standalone `Esp32Oled` driver, but no production caller or disclosure-acknowledgement flow exists, so first boot remains blocked in practice. The v0.2.43 target smoke build verifies the other adapters; the expanded OLED target linkage remains pending. **E29 is SIGNED** (`att`); **E31 is DELEGATED** (channel 1); **E30 is DELEGATED** to no remote rotation/reset and fail-closed service recovery (not implemented).
## 2. LittleFS `IFileSet`

| Logical data | Proposed file | Core interface | Required behavior | Status |
|---|---|---|---|---|
| Monthly event log | `/log/YYYYMM.bin` | `countChecked`, `monthKeyChecked`, `fileSizeChecked`, `readFile`, `appendFile`, `addFile` | Every metadata/read/write failure must be explicit; append complete 16-byte groups and verify completion; preserve month ordering | v0.2.57 adds POSIX/VFS-backed `LittleFsFileSet` for non-destructive operations; 20 adapter + 14 MonthSet native tests pass. ESP32 target, actual LittleFS, and power-loss behavior remain unverified |
| Corrupt-file quarantine copy | `/quarantine/...` | `quarantineCopy` | Copy and verify before altering original | Driver absent; power-loss behavior unverified |
| Later-file quarantine | `/quarantine/...` | `quarantineFrom` | Preserve every moved file and source identity; no data loss on interruption | Driver absent; power-loss behavior unverified |
| Tail repair | Current month file | `truncateFile` | Only after quarantine operations and explicit recovery flow | `LittleFsFileSet::truncateFile()` deliberately returns false; recovery remains unavailable |

`lib/littlefs_file_set/src/littlefs_file_set.*` implements the non-destructive subset against the mounted POSIX VFS path. It validates canonical `YYYYMM.bin` entries, rejects symlinked mount roots and month files, uses checked metadata, `pread()` for reads, `O_APPEND`/`write()` for full 16-byte record groups, then `fsync()`, size verification and read-back before success. It does not mount LittleFS or own its lifecycle. The caller must supply the actual mountpoint and serialize every operation; there is no internal mutex or global owner.

The host suite uses a temporary host filesystem, not an ESP32 LittleFS partition. An append/write/sync/close failure may occur after bytes have changed the file; `false` does not mean rollback. `LogStore` latches its append fault, but boot repair and quarantine cannot proceed because all three destructive methods return false. A torn tail therefore fails closed and remains unchanged. A close error in the reviewed `joltwallet/esp_littlefs` v1.22.3 VFS implementation can leave its descriptor cache entry allocated; treat it as a fatal storage fault and do not retry close blindly. Target compile/link, actual mount integration, injected VFS errors, descriptor recovery, and power-cut behavior are not verified. Source reference: https://github.com/joltwallet/esp_littlefs/blob/v1.22.3/src/esp_littlefs.c.

Never auto-format. No rename, copy, truncate, or directory operation may be described as atomic until C13's power-cut test proves the exact ESP32 LittleFS version and operation sequence. The existing `MonthSet::repair()` operation is not a substitute for that proof.

## 3. Backup cryptography (`ICipher`)

| Core method | Required primitive | Inputs/outputs | Status |
|---|---|---|---|
| `deriveKey` | PBKDF2-HMAC-SHA256 | Passphrase, 16-byte salt, iteration count, 32-byte key | Adapter absent; iteration count deliberately unchosen (C12) |
| `seal` | AES-256-GCM | 12-byte nonce, AAD, plaintext, ciphertext, 16-byte tag | Adapter absent; target availability/performance unverified (U15) |
| `open` | AES-256-GCM authenticated decrypt | Same AAD/nonce and tag; no unauthenticated plaintext may escape | Adapter absent |

Salt and nonce must come from a cryptographically secure device RNG. Reject malformed parameters and counts outside the core's 1,000..5,000,000 range. Do not choose the production iteration count until device timing and a threat-model review. Clear transient key material on every success/failure path. The toy cipher in host tests is logic scaffolding only.

## 4. HTTP `/api/v1` adapter map

The core API enum is authoritative for operations; exact URI spellings, JSON field names and response schemas are not yet signed. Do not implement guessed JSON shapes as if approved.

| Core endpoint | Access requirement | Adapter responsibilities / blockers |
|---|---|---|
| `EP_STATUS` | Public | Basic non-sensitive health/status only. Exact allowlisted fields still need definition (U20). |
| `EP_LOGIN`, `EP_LOGOUT` | Login public; logout token | Rate-limit PIN/setup attempts; issue/revoke RAM-only token. |
| `EP_PIN_CHANGE` | Token + current PIN | Require old PIN; persist lockout failure count before verification; never allow token-only takeover (C6). |
| `EP_PIN_RESET`, `EP_SETUP` | Setup code + health rules | Persist failed-attempt count before verification; enforce lockout and one-time/setup state. |
| `EP_DAY`, `EP_ROSTER_GET`, `EP_CONFIG_GET`, `EP_EXPORT` | Token | Filter secrets and enforce health permissions. |
| `EP_ROSTER_SET`, `EP_MARK`, `EP_NOCLASS`, `EP_CLOCK` | Token | Validate through pure core logic; append one durable event group; report success only after verified append. |
| `EP_CONFIG_PUT` | Token + expected generation | Validate allowlisted fields; derive current `windowOpen` with `deriveConfigWindowOpen()` from trusted RTC; `unclosedPast` is unavailable until C17/E2 is resolved. Reject schedule-changing requests until C17/E2 and the E26 source changes are verified; `apiDayInInclusiveTerm()` must be applied by any day-view/read route. Then use `ConfigApplyCoordinator`. |
| `EP_ENROLL` | Token + health/enrollment gate | Idempotency `req_id`; enforce O11 batch verification toggle; reserve shared AS608 runtime; keep disabled until U5/E18 are resolved. |
| `EP_BACKUP_ACK` | Token | Match outer backup CRC/length only after writer `finished()`. |
| `EP_RESTORE`, `EP_ROLLOVER` | Token + setup code and typed confirmation where required | C2 restore orchestrator and atomic swap are not implemented; refuse until complete. |

All administrative endpoints require a valid token and must pass `authorize()` before revealing state. Route every six-digit PIN/setup-code check through the appropriate long-lived `PinAuthCoordinator`; do not verify a secret separately or bypass the injected success action. The coordinator persists the attempt count before invoking the verifier, persists a reset before the success action, and requires the current PIN for PIN change. A storage/verifier/indeterminate-action fault must make protected routes unavailable; any partially issued session must be revoked or unusable. `GET /status` is the only public endpoint per signed O5. This is an adapter acceptance contract, not current production enforcement.

### PIN-attempt coordinator requirements (v0.2.31 core helper; NVS attempt-store source added in v0.2.34)

- Construct the coordinator before accepting login, setup-code or current-PIN requests; call `boot()` and refuse those routes if its counter cannot be loaded.
- Use the E12-approved counter domain and one long-lived instance per domain. E12 remains DELEGATED; do not decide shared-versus-separate counters in the adapter by accident.
- `Esp32NvsPinAttemptStore::persistFailureCount()` checks that the key already exists, then calls `nvs_set_u16()`, `nvs_commit()`, closes the write handle, reopens read-only and compares the exact value. Missing or wrong-type keys fail closed. The host fake uses ESP-IDF's `ESP_ERR_NVS_TYPE_MISMATCH`. The user-supplied v0.2.36 full native run passed 413/413 cases, including the NVS suite; this remains host-fake evidence only, not target ESP32 or power-loss verification.
- `Esp32PinAuthRuntime` owns this store and the `PinAuthCoordinator` built from it. It must start only after `ConfigBootCoordinator::start()`: when config is `NEEDS_SETUP`, it reads first and initializes only on `ESP_ERR_NVS_NOT_FOUND`; this preserves a counter across interrupted first provisioning. When config is `READY`, a missing counter makes coordinator boot fail and is never recreated. Config `COLD`/`FAULT` states are rejected. The owner is one-shot.
- The verifier distinguishes mismatch from internal/crypto error. Only mismatch is an ordinary bad-secret result; verifier errors latch the coordinator.
- Session issuance must occur only inside the success action after the persisted counter reset. v0.2.38 `TokenSessionSuccessAction` preflights without mutating `TokenTable` and inserts only after the complete response write is confirmed. Pass a fresh monotonic timestamp at that point so the 900-second idle lifetime starts on activation. An aborted response therefore cannot evict an existing session. The route must serialize TokenTable mutations between preflight and confirmation and erase its temporary token copy. Confirmation means the server API reports the full response write succeeded; it is not proof the phone application received/stored the token. If the chosen HTTP API does not expose full-write success, use a lower-level write path or add an explicit activation handshake. If the post-write insert unexpectedly fails, treat login as failed and latch the production authentication/service fault; do not report success. On any indeterminate result, make all protected routes unavailable and ensure no session from the uncertain action is usable. The ESP32 RNG adapter must be notified only after successful RF startup; do not use `esp_fill_random()` before a continuous entropy source is available.
- PIN change must pass through `changeAdminPin()`; the writer stores only the derived salted credential and verifies its durable commit. Raw PIN persistence is forbidden.
- Serialize the complete operation. If the future server uses multiple tasks, hold one mutex around the whole coordinator call. The adapter does not make read-modify-write atomic against a second independently constructed writer; use one owner/coordinator per namespace and do not write the counter elsewhere.

## 5. Composition order (not yet implemented)

1. Initialize NVS through `Esp32NvsConfigBackend::begin()`, then call `ConfigBootCoordinator::start()`. Construct no runtime from defaults. Stop on `CFG_BOOT_FAULT`. Construct one `Esp32NvsApCredentialStore`, one `Esp32BootstrapRandom` and one `ApCredentialBootstrap`; call `prepare()` with the exact boot state and the validated `Config::wifiPass` only in `CFG_BOOT_READY`. On `CFG_BOOT_NEEDS_SETUP`, the bootstrap returns the stored/generated WPA2 passphrase with `disclose=true`; the production setup caller must render it on the OLED before provisioning may transition to READY. Use the same passphrase in the first `Config::wifiPass` written by `ConfigProvisioner`. Clear transient copies and never log or expose the secret through public status.
2. Use the E29-fixed SSID `att` and E31 channel 1. Only after successful credential bootstrap, construct exactly one `Esp32WifiAp` and start it with those constants and the durable passphrase. The AP must install WPA2-PSK/CCMP before `esp_wifi_start()`. `Esp32BootstrapRandom` must run before radio/ADC/I2S activity; `Esp32SecureRandom` becomes available only after AP_START. Keep the AP owner, both RNG adapters, display disclosure and TokenTable mutation on one serialized task. Do not call Arduino `WiFi.mode()` / `WiFi.softAP()` independently.
3. After config boot establishes READY or NEEDS_SETUP, construct one `Esp32PinAuthRuntime` per E12-approved counter domain and call `start()` before accepting login, setup-code or current-PIN requests. Expose no protected route unless every required auth runtime is ready. Run the NEEDS_SETUP flow and `provision()` with a real setup/health authorization gate; only state READY exposes the validated config/slot selection. On BOOT_FAULT or auth-runtime fault, map to the appropriate health fault and stop protected operations. Do not construct runtime from defaults after a config fault.
4. Mount LittleFS without formatting; open `MonthSet`/`LogStore`; verify log health.
5. Attach `RosterStore`, `LogAttendanceAdmission`, and `ClosureEngine` to the same `LogStore`; fail closed on observer exhaustion or replay fault.
6. Read RTC and update `HealthFsm`.
7. Construct exactly one `As608Runtime` for the physical sensor. Construct `As608AttendancePipeline` with the signed page resolver only after E18 is resolved and U5 verified.
8. Construct `AttendanceConfigRuntime` and `ConfigApplyCoordinator` with the selected config and slot generation.
9. Run one serialized main loop: service RTC/health, one sensor step, pipeline result, closure tick, web server service, OLED/buzzer. No parallel task may operate the sensor, log, config, pipeline or closure engine without an explicit synchronization design.

This composition order is a design target, not a firmware implementation. Production `main.cpp`, drivers, scheduler and UI remain absent. E30 is DELEGATED to no reset/rotation API and fail-closed behavior. A physically supervised USB recovery procedure is not implemented; do not add a delete/overwrite path without a transaction spanning the NVS credential and authoritative Config slot.

## 6. Config boot and schedule gate (v0.2.16)

`updateHealthFromConfigBoot()` maps config boot state to `HealthFsm`; `deriveConfigWindowOpen()` computes the current scan-window fact from validated config and trusted RTC time. It uses the timetable's window rules without applying term bounds, so it may conservatively report a window outside the configured term. There is intentionally no `unclosedPast` adapter yet. C17 records that the current timetable cannot safely reconstruct historical sessions after a schedule change because its effective-from boundary is not persisted. E26 now selects an inclusive term end and source aligns API mutation, scan and closure boundaries; the current regressions are NOT RUN and no production day-view route exists. C17/E2 still blocks historical `unclosedPast`. Reject schedule changes until E2/C17 and E26 verification are resolved.

### OLED shared-bus adapter (v0.2.44)

`Esp32Oled` is a standalone adapter for the fixed 128x32 SSD1306 panel at I2C address `0x3C`. It takes an injected `TwoWire&`; it deliberately does not call `Wire.begin()` because SDA 21/SCL 22 are shared by the OLED, DS3231 and EEPROM. The future board composition root must initialize the bus exactly once before calling `Esp32Oled::begin()`. SSD1306 transactions are requested at 100 kHz; the constructor sets both the temporary and restored bus clocks to 100 kHz.

`begin()` calls `Adafruit_SSD1306::begin(SSD1306_SWITCHCAPVCC, 0x3C, true, false)`. The `periphBegin=false` argument avoids reinitializing the already-owned bus. `EOI_BUFFER_READY` means the Adafruit driver allocated its framebuffer and issued initialization commands; the API does not provide a reliable panel-presence/result signal here.

`showSetupCredential()` accepts only `ApCredentialResult{APCB_OK, true}` and exactly 32 lowercase-hex bytes, matching E28's generated credential. It renders four 8-pixel rows: title, label, first 16 hex characters, second 16 hex characters. Non-disclosure/failure/invalid-secret calls request a blank frame, preventing an old key from intentionally remaining on screen when the caller moves to READY/fault. After the credential frame transfer request, the driver clears the software framebuffer but leaves the physical panel image until `clear()` is called. No second plaintext string is constructed, and the caller's buffer is untouched.

Critical limitation: Adafruit SSD1306 `display()` returns `void`. `EOA_TRANSFER_REQUESTED` means only that the library call returned; it does **not** prove that the I2C writes were ACKed or that the physical panel showed/cleared the image. The display cannot by itself satisfy a verified disclosure gate. The production boot caller must remain fail-closed and a target/device-visible acknowledgment strategy is still required before `NEEDS_SETUP` can transition to `READY`. No caller exists yet.

The smoke project pins Adafruit SSD1306 2.5.17, Adafruit GFX 1.12.6 and Adafruit BusIO 1.17.4. Their `library.properties` dependency chain is SSD1306 -> GFX -> BusIO. The user-confirmed v0.2.43 smoke build covered the earlier ESP32 adapters; the v0.2.44 smoke build must be rerun to validate these exact library APIs/linkages. See `docs/SPECS/esp32_oled.md`.
